## [0.1.3] - 2026-10-28

### Security
- Agent-instruction files no longer count as docs. An agent PR that adds, edits, renames or deletes `AGENTS.md`, `CLAUDE.md`, `GEMINI.md`, `.cursorrules`, `.cursor/**`, `.claude/**`, `.github/copilot-instructions.md` or another file in the new `paths.agentInstructions` list (matched ignoring case) is the `agentInstructionsEdited` tamper rule (`HUMAN`, no retry); before, a `*.md` instruction file matched `paths.docs`, so a docs-only PR rewriting the instructions every later agent run follows could auto-merge once docs was trusted.
- `check --test-user <name>` runs the PR's proof tests as a separate, unprivileged OS user (through passwordless sudo, Linux and macOS), and kills every process that user still runs before the gate reads the proof or writes anything. Before, the tests ran as the gate's own user in the same job as the verdict file, so a test that forked a background process could forge the verdict file (and its `proven` bit, the one fact `apply` trusts) or a later step's code after `check` had decided. The test user owns only the proof worktrees and a scratch `HOME` while they run; The checkout's `node_modules` is mirrored for it with hard links into a readable temp dir (the runner's home is `0750`, so the test user cannot reach the checkout), and `check` refuses to start when the user or passwordless sudo is missing. The PR workflow template's gate job now creates `mergeproof-tests` and passes `--test-user mergeproof-tests`; re-run `mergeproof init --force` to pick it up (it needs a mergeproof release with this flag behind the `uses:` ref).
- Feature and bugfix proofs now compare test-case counts too, not just refactors. They run the full suite on base (with the PR's new test files checked out, so an honest PR counts the same cases on both sides) and on head, and fewer cases on head is the `testCountDropped` tamper rule (`HUMAN`, no retry). Before, a feature PR could add one proving test while deleting the entries of a `src/` list other tests generate their cases from. This adds one full-suite run on each side to feature and bugfix proofs; counts that don't parse are still skipped.

### Changed
- README usage now leads with the two-job gate/apply workflow, and the single-process `check <pr-url>` is marked local-only.

### Added
- `docs/releasing.md`: what to settle before the first npm publish (repository visibility, the `NPM_TOKEN` secret) and how to cut a release.
- `agents.identities` in `.mergeproof.json` maps an agent login to its own trust bucket, e.g. `"agy-bot": { "agent": "agy", "model": "gemini-4-argon-high" }`. `check` and `apply` use it for PRs by that login instead of the `--agent`/`--model` flags (the flags stay the fallback), so one workflow can gate several agents in separate buckets. Like the rest of the config it is read from the base branch tip; each login must also be in `agents.logins`.
- `mergeproof dispatch <issue> --harness agy [--model <label>] [--dry-run]` runs the Antigravity CLI (`agy -p`) on an issue from a maintainer's machine. It builds the same trusted issue file as the issue workflow (an untrusted author's title and body need an explicit `--vouch <digest>` naming the exact issue file the maintainer read; comments only from trusted authors), runs agy in a throwaway worktree on a new `agent/issue-<n>` branch with the identity account's token from `MERGEPROOF_DISPATCH_TOKEN` in its environment only, and leaves the PR to the normal gate. It never decides a verdict.
- The issue workflow can run agy instead of Claude Code: `MERGEPROOF_HARNESS=agy` (default `claude`; `agy` requires `MERGEPROOF_AGENT=agy`, any other value stops the run). It downloads one pinned agy release and fails unless its SHA-512 matches (`MERGEPROOF_AGY_URL` / `MERGEPROOF_AGY_SHA512` override the pin), never Google's `install.sh`, which installs the newest release against a hash from the same host. agy runs headless with no tool deny-list, so the agy path is split across three jobs: `agent` builds the trusted issue file and uploads it as a one-day artifact (on a retry its context step also resolves the pull request's head branch), `agy-run` runs agy with the claude prompt (two substitutions: commit and write the PR title/body/stop comment into a handoff directory instead of pushing, because it has no GitHub access) holding only the Gemini key in its environment (no `GH_TOKEN`, no bot token, no credential helper, `contents: read`, no `gh` call), inside a container pinned by digest (`MERGEPROOF_AGY_IMAGE`, default `node:22-trixie@sha256:…`; capabilities dropped) on a copy of the checkout, so a prompt-injected agent can leak the model key but holds no GitHub write credential, cannot reach the runner's Actions runtime token or cache, and has no credentialed later step to hijack; only plain files with known names leave the container; it leaves a `git bundle` of the `agent/*` branch plus the handoff files as another one-day artifact, and `agy-publish` (which never runs agy, npm or repo code) validates that untrusted artifact before anything is pushed: the bundle verifies and holds exactly one branch named `agent/<kind>-<issue>-<slug>` (on a retry, also exactly the pull request's head branch; fork pull requests are never retried), descends from the default-branch tip (a retry fast-forwards the current head, never forces it), touches nothing under `.github/`, `.mergeproof.json` or `.mergeproof/` (raw paths with renames split; the bot PAT never pushes workflow or gate files), the title is one non-empty line of at most 200 characters without control characters and the body and stop comment at most 60000 bytes, relayed to gh only via `--title` from a file-read variable and `--body-file`; only then does it push, open the PR (a retry just pushes), post the stop comment as the bot and the dispatch marker with `github.token`, while a refused output, a broken validation or a failed push comments on the issue and labels `needs-human`. Runs for one issue now queue as whole runs (a workflow-level concurrency group; label events for other labels get their own group so they never displace a real run), instead of per job. The issue file never trusts comments by `MERGEPROOF_BOT_LOGIN` (on either harness), so an agent's own stop comment cannot come back as maintainer text. The template comments name the supply-chain and deny-list risks. Re-run `mergeproof init --force` to pick up the new template.

### Fixed
- `sync` finds reverts that do not say `This reverts commit <sha>`: a commit with `Reverts owner/repo#N` on its own line (GitHub's revert-PR body, kept when the revert PR is squashed with its description), or one whose change is the exact undo of the merge (same `git patch-id --stable`) under any message, such as a revert made by hand. Both must land after the merge, and a PR reference must name this repo. Before, a revert squashed under another message, or written by hand, left the outcome `clean`, so the agent kept trust it had lost. A revert squashed together with other changes is still missed.
- A crash between the merge and the ledger write no longer loses the outcome. `land()` now writes the open outcome before it merges and records the merge after, and the PR workflow pushes the ledger even when apply failed (re-run `mergeproof init --force` for the template change). A merged PR whose run died mid-way is left `open`, and `sync` turns it into `pending` once it sees the PR merged. Before, the outcome was written only after the merge, and the push step was skipped when apply failed, so a crash or network error left a merged PR with no ledger entry.
- CI still running in another workflow no longer turns a proven PR into RETRY. `check` and `apply` now wait for pending CI, re-reading it every 30 seconds for up to `limits.ciWaitSec` (default 600, `0` turns the wait off), pinned to the gated head (a head that moves stops the wait). CI still pending after the wait is HUMAN, not RETRY, because the agent cannot fix a slow workflow, and `apply` may lower a MERGE file to that HUMAN.
- A new helper, fixture or snapshot added under a test glob no longer makes a feature or bugfix RETRY with "passes on base, so it proves nothing". Files matching the new `paths.testSupport` globs (default: `fixtures`, `__fixtures__`, `__snapshots__`, `__mocks__` and `helpers` directories, `*.snap` and `*.json`) still count as test paths for the kind but are never run as new tests (a file named `*.test.*` or `*.spec.*` is always a test, even under `helpers/`); they are still copied into the base worktree for the new tests that import them.
- The release workflow fills the GitHub Release notes from the tagged CHANGELOG section again: under the regex "m" flag a bare `$` matched the first line end, so v0.1.1 and v0.1.2 shipped with empty notes (both were filled in by hand).

## [0.1.2] - 2026-10-23

### Security
- The issue workflow no longer lets the agent read the issue from GitHub, where anyone who can comment (on a public repo, anyone at all) could inject instructions, and where an untrusted author can edit their issue after a writer labels it. The context step now writes `$RUNNER_TEMP/mergeproof-issue.md` — the agent's only issue text: the title and body when the author is in `MERGEPROOF_AUTHORS` or a write/maintain/admin collaborator (a label-vouched untrusted author only while the title and body are unedited since the last `agent` label, checked through GraphQL `lastEditedAt` and rename events, and only when a trusted user added that label; a later edit or rename, the label's removal, or an unreadable history stops the run with an error and a comment asking a writer to re-apply the label), comments only from trusted authors (never `github-actions[bot]`), each piece fenced under a heading naming its author, with a final count of the omitted comments. The prompt points the agent at that file, frames it as a task description rather than instructions that override the rules, forbids fetching issues, PRs, comments or web pages with `gh`, `curl` or web tools, and keeps every standing rule; retries read the gate's latest verdict comment on the pull request (anchored to the shape apply posts) from the same file instead of following a URL; `claude_args` additionally disallows `WebFetch`, `WebSearch`, `Bash(gh issue view:*)`, `Bash(gh api:*)` and `Bash(curl:*)` (defence in depth — the exact flag syntax must be checked against the pinned `anthropics/claude-code-action` version). The skills read the issue the same way (bugfix/feature skill version 2). Re-run `mergeproof init --force` to refresh installed copies.

## [0.1.1] - 2026-10-23

### Fixed
- The PR workflow's apply jobs no longer share one concurrency group. GitHub keeps one pending job per group and cancels the rest, so when several verdicts arrived at once only the first and the last landed (no merge, comment, label or ledger entry for the others). Each PR now gets its own group, and a ledger push that loses the race records its outcomes again on top of the newest ledger and retries, instead of a `git rebase` that conflicts on the JSON. Like `appendOutcome`, it never doubles or overwrites a settled outcome; that push fails instead.
- `apply` landed an honest gate HUMAN for a tamper note (say, an edited existing test) as "verdict file disagrees with the re-check", as if the artifact were forged. A HUMAN with no proof now lands as that HUMAN with its notes; any other verdict carrying a tamper note is still refused.
- The action split its `args` with `read -ra -d '' argv`, where `-a` took `-d` as the array name: every `check`/`apply`/`sync` run got no arguments and failed with a usage error. Now `read -r -d '' -a argv`, and a test runs the real script in bash.
- `mergeproof-pr.yml` computed the next attempt as `${{ fromJSON(...) + 1 }}`; GitHub expressions have no arithmetic, so GitHub rejected the whole file and the gate never ran. The shell counts it now, and a test bans arithmetic in expressions. Re-run `mergeproof init --force` to refresh an installed copy.
- The PR workflow's gate and apply jobs get `statuses: read`: the CI rollup includes commit statuses, and once any other app (a review bot) posts one, GitHub refused the whole query and the gate failed with "Resource not accessible by integration". The same query reads the workflow run behind each check suite, so the gate job also gets `actions: read`.
- The release workflow sets a git identity before creating the annotated `v1` tag (the v0.1.0 run failed there), and `main-guard` gets `checks: read` so it can see CI results.

## [0.1.0] - 2026-10-23

### Fixed
- CLI and adapter edges: `--` ends flag parsing instead of erroring; PR URLs with browser suffixes (`/files`, `?w=1`, `#fragment`) parse; and the proof-run fingerprint now also covers `.git`'s `refs/`, `HEAD`, `packed-refs` and `objects/info/alternates`, closing the same shared-`.git` write class as hooks and config.
- `check` in `mode: off` no longer comments on the PR: off now means off for both halves of the split (apply already wrote nothing).
- `sync` opens the human-triage regression issues before settling the ledger: a failed issue creation used to mark the outcome reverted on disk anyway, permanently losing the triage issue; now the outcome stays pending and the next sync retries it (the residual failure mode is a visible duplicate issue).
- Git diff prefixes are pinned (`diff.noprefix=false`, `diff.mnemonicPrefix=false`, `srcPrefix`/`dstPrefix`): a machine's noprefix setting emitted `+++` headers the added-line parser misread, corrupting skip-marker note paths.
- Colored test output no longer disables the dropped-test-count check: `parseTestCount` strips ANSI escapes (SGR, cursor, OSC) before matching, and proof runs set `NO_COLOR=1` with `FORCE_COLOR=0` (CI often forces color on, and FORCE_COLOR overrides NO_COLOR in several runners), so a refactor that makes test cases disappear cannot hide behind a colored summary.
- Renaming a manifest away (`package-lock.json` → `old/package-lock.json`) classifies as `deps`, not `refactor`: classification now sees a rename's old path too, so a manifest cannot be walked out of the never-auto-merged bucket.
- Trust can no longer be diluted by pending merges: the recent-revert window in `trustFor` now counts settled outcomes only, so a run of merges still inside their revert window cannot push a revert out of the window and restore an agent's trust before any of them settles (the documented "pending merges count toward neither" rule, now actually enforced).
- The gate job authenticates its git fetches for private repos: `persist-credentials: false` (kept, so PR test code cannot steal checkout credentials) leaves git unauthenticated, and `check` fetches the PR and base refs over the network. A `gh auth setup-git` step with the job's read-only `github.token` now configures the credential helper before the gate runs; public repos are unaffected, and the test environment's `*TOKEN*` scrubbing keeps the token away from PR code.
- Template hardening: the composite action reads its whole `args` input across newlines (`read -ra -d ''`); the context job parses each bot comment as one JSON string (`@json`), matches the dispatch marker against the strict `<!-- mergeproof-dispatch issue=<n> skill=<name@version> -->` pattern, and counts `Mergeproof — RETRY` once per comment (echoed text and CRLF can no longer forge markers or inflate the attempt count); the context job takes the CI'd SHA from `workflow_run.head_sha`; and the apply job lands with the job's `github.token`, never the agent's bot PAT — its verdict comments must be `github-actions[bot]`-authored for the attempt count to work (with the bot PAT the counter never incremented and retries looped forever), and the agent's token must never be what merges. Accepted trade-off, documented in `templates/README.md` and `SECURITY.md`: a mergeproof merge does not itself trigger the repo's push workflows — the gate pins the merged head's CI instead.
- The workflow now pins the gated head end to end: `check` and `apply` take `--head <sha>` (the head whose CI completed, from the triggering `workflow_run` event). A PR that moved after its CI makes `check` stand down — `HUMAN`, no proof runs, nothing written, and the verdict file names the CI'd commit with `proven: false` — so `apply`'s moved-head refusal supersedes the stale run with no label, comment or merge, and the push's own CI starts a fresh gate. Previously the gate judged the live head, whose checks read `none` (the local-suite fallback), and `apply` treated `none` as proof-OK: a merged commit could skip the repo's CI entirely. `apply` also refuses (as tampering) a verdict file whose head disagrees with the workflow's `--head`. The stand-down verdict carries no kind at all — after a force-push the CI'd commit may be gone, and apply refuses a moved head before reading kind — instead of crashing in the diff.
- `check` and `apply` now read the gate config and the merge-base from the fetched `refs/mergeproof/base` tip — one coherent snapshot — instead of the PR API's base SHA, which can lag the fetch and make the two jobs derive from different commits.
- The PR workflow's bot-comment fetch fails closed: a swallowed `gh api` failure (the old `|| true`) read as zero comments, resetting the attempt count to 1 and dropping the dispatch marker — re-dispatching an agent that had already been told to retry. The marker and count greps keep their `|| true`, because grep exits 1 on zero matches and zero is a valid answer.
- The release workflow creates the GitHub Release only when it is missing: `gh release create … || echo "already exists"` also swallowed real failures (auth, API) at a point where the `v1` tag had already moved, hiding a broken release.
- The release workflow skips `npm publish` with a warning when `NPM_TOKEN` is not set, so the `v1` tag and the GitHub Release still land; re-run the tag after adding the secret to publish.

### Security
- The issue workflow's daily cap now stops the run for real: hitting the cap used to `exit 0` inside the context step, which only ends that step — the agent step still ran, with the model key, on empty outputs. The context step now emits a `stopped` output, and the agent and marker steps require `success() && steps.ctx.outputs.stopped != 'true'` (`success()` is load-bearing: a bare `if:` replaces the default success check, so a *failed* context step would otherwise still start the agent). The run count uses `--limit 200` and fails closed at a full page, so the cap can no longer be under-counted past the default page size.
- `main-guard` workflow (this repo): every push to `main` is checked; a force-push, a commit outside any merged PR, or a PR merged without green GitHub Actions checks on its head fails the job and opens an issue. A detective control, because free private repos cannot have branch protection.

### Added
- `mergeproof init` (M2 flow 1): detects the install command, test command, test paths and PR CI workflow; writes `.mergeproof.json` (always `mode: shadow`), the three workflows with placeholders filled and the bugfix/feature skills; idempotent, `--force` to replace drifted files, `--dry-run` to only plan.
- With `--yes` (or an interactive `y`) `init` creates the `agent`/`needs-human` labels, sets the agent/model/bot-login variables and stores `MERGEPROOF_MODEL_KEY`/`MERGEPROOF_BOT_TOKEN` from the environment over `gh secret set` stdin, redacted from any error. A read-only check reports branch protection, merge restrictions (incl. the github-actions app), the bot permission and token guidance; it never changes protection.
- README: hero and pipeline visuals (`assets/readme/`, shipped in the npm tarball), badges and a verdict/exit-code table.
- M2 GitHub Action and workflow templates: `action.yml` (`ahmed-3m/mergeproof@v1`) validates its `command`, runs `bin/mergeproof.mjs` with `args` passed through the environment and split without shell expansion, and exposes the CLI's exit code as an output. `templates/workflows/` ships `mergeproof-pr.yml` (workflow_run → context → read-only gate job → write-only apply job, ledger pushed to the `mergeproof-ledger` branch, agent re-dispatch on RETRY, `needs-human` when retries run out), `mergeproof-issue.yml` (allowlisted authors or maintainer `agent` labels start the agent with the per-kind skill; posts the `github-actions[bot]` dispatch marker) and `mergeproof-sync.yml` (nightly ledger settle). `templates/README.md` documents the placeholders, repo variables and secrets; the new workflows suite (`tests/workflows.test.mjs`) checks the templates' safety invariants — kill switch on every job, `set -euo pipefail`, no user text interpolated into any `run:` script — one-line runs included — SHA-pinned actions, read-only gate.
- M2 skills: `skills/bugfix/SKILL.md` and `skills/feature/SKILL.md` — per-kind playbooks (proof-first test, the tamper rules, `check --local`, a fresh-context critic pass, a self-review PR body) that skill-aware harnesses load and other harnesses read as prompt instructions. `skills/README.md` documents usage; the workflow logs them to the ledger as `--skill <name>@<version>`, and the structure suite validates the frontmatter.
- Split the gate for CI (M2): `check <pr-url> --verdict-out <file>` runs the gate with no writes at all — no merge, no comment, no ledger write — and writes a `mergeproof-verdict@1` JSON file for a separate write job. `--verdict-out` with `--local` is a usage error.
- New `apply <verdict-file> --pr <pr-url>` command (`--dry-run`, `--json`, `--ledger`, plus the gate's `--agent`/`--model`/`--skill`/`--attempt`/`--issue` flags, `--agent` and `--model` required): the write half of the split, which never runs PR code. The verdict file is written in the job that ran PR code, so it is trusted for one fact only — that the proof held. apply re-derives kind and the tamper rules from the fetched diff (shared `inspect()`), re-decides with its own ledger and a fresh CI read, and requires the workflow's flags to match the file. A closed/moved/non-agent PR or `mode: off` is a `HUMAN` refusal with nothing written; a file that disagrees with any re-check is a `HUMAN` refusal that comments and labels `needs-human` (new `gh addLabel`), with nothing merged or logged. Otherwise it lands like `check` (shared `land()`): outcome recorded when proven, merge (MERGE + enforce) pinned to the gated head SHA with the trailer, ledger written, re-derived verdict commented; a MERGE whose CI went red lands as RETRY — apply can lower a verdict, never raise one. Note text from the file is validated (≤ 3 notes, ≤ 300 chars, no newlines/backticks/control chars) and never posted.
- Refactor proof now runs the full suite on head as well (green on base and head, per flow 2) and compares test-case counts, parsed from node:test (spec/TAP), jest, vitest and pytest output: fewer cases on head than base is the `testCountDropped` tamper rule, so a refactor can no longer make tests disappear by deleting the data they generate from. Counts that don't parse are skipped, so unknown runners keep working.
- M1 gate: `check <pr-url>` and `check --local` run classify → tamper → prove → decide. Per-kind proof runs in throwaway git worktrees: new test files must fail on base 2/2 and pass on head 3/3. Enforce mode merges pinned to the proven head with a `Mergeproof-Verdict` trailer. Every proven PR is logged to `.mergeproof/ledger.json`, so human merges earn trust too.
- `sync` settles the ledger (open → pending → clean or reverted) and opens a human-triage issue for each revert.
- Config is `.mergeproof.json` (YAML later), validated strictly and read from the base commit. New keys: `testFileCommand`, `issueLabels.bugfix`, `limits.testTimeoutSec`.
- Tamper rules: unsafe file names, gate-file edits, edited, renamed or deleted tests, skip/only markers, kind claims that disagree with the paths, oversized diffs.
- `check` flags `--base`, `--agent`, `--model`, `--skill`, `--attempt`, `--ledger`; `sync` flags `--dry-run`, `--ledger`, `--ref`.
- The 8 pre-registered benchmark scenarios run end to end in `tests/benchmarks.test.mjs`; seeded `demo/ledger.json`.
- `npm run demo` (`demo/build.mjs`) builds a throwaway sample repo with the four demo PRs and prints the gate's verdicts with the seeded ledger and from a cold start; it exits 1 on any unexpected verdict.
- `check --issue <n>`: the issue the workflow dispatched the agent for.
- Project scaffold: CLI entry with `check` and `sync` commands, verdict contract (`MERGE | RETRY | HUMAN`) and exit codes, config defaults, stubbed pipeline modules (classify, tamper, prove, decide, ledger, trailer) and adapters (process, git, gh, runner).
- Specs: `PROTOTYPE.md` (M1 core CLI) and `briefs/m2-autopilot.md` (M2 package).
- Tests for the CLI, verdict formatting, flag parsing and repo invariants; CI on Node 18/22/24 for Linux and Windows.

### Changed
- `check --local --issue` is now a usage error.

### Security
- Test runs drop credential-like environment variables and `NODE_TEST_CONTEXT` (an inherited value made a nested `node --test` exit 0 on failure).
- An agent PR now needs an author in `agents.logins`; a branch named `agent/...` alone no longer qualifies, and fork PRs always go to a human.
- The gate config is read from the base branch tip instead of the merge-base, so a PR can't dodge a config change made after it branched.
- Git runs with hooks and fsmonitor off, and `.git/config`, hooks, `info/` and the ledger are fingerprinted around the proof runs; a change made by PR test code is `HUMAN` and nothing is logged. The ledger is read once, before PR code runs.
- The feature/bugfix bucket comes from `--issue` only; the PR's own "closes #N" links are no longer read.
