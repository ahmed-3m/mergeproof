# Security

## Reporting a vulnerability

Please open a private security advisory on the GitHub repository rather than a public issue.

## Threat model (draft, kept current as features land)

mergeproof decides whether code written by an AI agent may be merged, so it treats every PR as untrusted input.

| Threat | Mitigation |
|---|---|
| Agent edits or deletes tests to get a green run | Tamper rules block it with a `HUMAN` verdict; no retry |
| A refactor, feature or bugfix makes test cases disappear without touching a test file (e.g. deletes entries of a list the tests generate their cases from) | Each of those proofs counts test cases on base (with the PR's new tests checked out) and head; fewer on head is the `testCountDropped` tamper rule (`HUMAN`, nothing logged) |
| New tests that prove nothing | Feature and bugfix tests must fail on base and pass on head |
| Agent mislabels a PR to reach a trusted kind | Kind comes from changed paths only; label mismatch is tampering |
| Compromised dependency passes every test | Deps PRs never auto-merge in v1 |
| Running PR code with secrets | Test steps run with no secrets and a read-only token; only the merge step can write (M2 workflows) |
| An untrusted issue starts an agent at all | Only allowlisted authors or maintainer labels start an agent; bot-written issues never do (M2) |
| Prompt injection through issue comments or an edited body | The agent never reads the issue from GitHub. Its only issue text is a file the issue workflow's context step builds: the title and body when the author is in `MERGEPROOF_AUTHORS` or a write/maintain/admin collaborator (or, for a label start, while its title and body are unedited since the last `agent` label — a later edit or rename, or the label's removal, stops the run and asks a writer to re-apply the label), comments only from trusted authors (never `github-actions[bot]`, which any workflow in the repo can post as); every other piece is dropped and counted. A retry adds the gate's latest verdict from the pull request, matched only in the exact shape apply posts. Each piece is fenced under a heading naming its author, so nothing can pose as someone else's text. The prompt frames the file as a task description (never as instructions that override the rules) and forbids fetching issues, PRs, comments or web pages; `claude_args` additionally disallows `WebFetch`, `WebSearch`, `gh issue view`, `gh api` and `curl` as defence in depth |
| Flaky tests faking proof | Repeat runs on base and head; quarantine list in config |
| PR loosens its own gate | Config is read from the base branch tip, not the PR or an older merge-base; edits to `.mergeproof.json`, `.mergeproof/**` or `.github/**` are tampering |
| PR claims a trusted agent or model | Agent and model come from the caller's `--agent`/`--model` flags, or from the author's `agents.identities` entry in the base-branch config, never from the PR |
| `mergeproof dispatch` runs a local agent (agy) on an issue | An untrusted author's title and body run only after the maintainer reads them and passes `--vouch <digest>`, a SHA-256 digest of the exact issue file they read, so a later edit is refused; comments are kept only from `MERGEPROOF_AUTHORS` or write/maintain/admin collaborators (never `github-actions[bot]`), fenced under headings naming their authors, like the issue workflow's file. The agent account's token comes from `MERGEPROOF_DISPATCH_TOKEN` and reaches the agent's environment only (never argv, a file or output), with every other token-, secret-, password- and API-key-shaped variable removed except agy's own `GEMINI_API_KEY`. agy runs with its permission prompts off, so it runs in a throwaway worktree on a new branch, never in the maintainer's checkout. That worktree is not a sandbox (agy runs as the maintainer's OS user and can read their other credentials), so the docs recommend a dedicated OS user, VM or container. Its PR goes through the normal gate |
| The issue workflow's agy harness (`MERGEPROOF_HARNESS=agy`) runs a binary from Google's servers | Google's installer installs the newest release and checks it against a hash from the same host, so a compromised host would pass its own check. The template never runs it: it downloads one release tarball (`MERGEPROOF_AGY_URL`) and stops unless it matches a SHA-512 pinned in the template or `MERGEPROOF_AGY_SHA512`, and sets `AGY_CLI_DISABLE_AUTO_UPDATE`. The pin was taken from Google's manifest and checked against a download, which trusts that host once; upgrades are the maintainer's job. agy runs with `--dangerously-skip-permissions` and has no tool deny-list, so the trusted issue file is the only prompt-injection control; the run is therefore split across three jobs. The `agy-run` job holds no GitHub credential at all (only the Gemini key; `contents: read`; no `gh` call), so an injected agent cannot exfiltrate a token and cannot plant a `gh`/`git` shim, `GIT_*` config or `LD_PRELOAD` for a credentialed step to inherit — the credentialed work runs in `agy-publish`, a fresh job that never runs agy, npm or repo code. `agy-run` commits locally and its output leaves as a `git bundle` plus handoff text files; `agy-publish` validates that artifact as untrusted data before anything is pushed: the bundle verifies against the default-branch checkout and holds exactly one branch named `agent/<kind>-<issue>-<slug>` (on a retry, also exactly the pull request's head branch; fork pull requests are never retried), its tip descends from the default-branch tip (a retry fast-forwards the pull request's current head, never forces it), its diff touches nothing under `.github/`, `.mergeproof.json` or `.mergeproof/` (raw NUL-separated paths with renames split, so no quoted name or rename hides a path; the bot PAT never pushes workflow or gate files), the title is one non-empty line of at most 200 characters without control characters, the body and stop comment at most 60000 bytes, and gh receives them only via `--title` from a file-read variable and `--body-file`. A refused output comments on the issue and labels `needs-human` with nothing pushed; a broken validation or a failed push does the same. Comments by `MERGEPROOF_BOT_LOGIN` (the agent's own stop comments) are never trusted issue text. agy itself runs in a container (`MERGEPROOF_AGY_IMAGE`, digest-pinned; capabilities dropped, `no-new-privileges`, the runner's own user) on a copy of the checkout, seeing only the issue file and the binary (read-only), the handoff directory and `GEMINI_API_KEY`, so it cannot reach the runner's Actions runtime token (no Actions cache poisoning), the runner's checkout or `$GITHUB_ENV`; the bundle is made in the same image and only plain files with the four known names are uploaded (a symlink would make the upload read a runner file). The container has network (the model API and npm), so the Gemini key remains leakable. `MERGEPROOF_HARNESS=agy` requires `MERGEPROOF_AGENT=agy`, so its PRs never land in another agent's trust bucket |
| Human or fork PR posing as an agent | An agent PR needs an author in `agents.logins`; a branch named `agent/...` alone is not enough, and fork PRs always go to a human |
| PR points "closes #N" at a labeled issue to pick a trust bucket | The bucket comes only from the `--issue` the workflow passes; the PR's issue links are ignored |
| PR test code plants a git hook, fsmonitor or filter, or rewrites the ledger | Git runs with hooks and fsmonitor off; `.git/config`, `hooks/`, `info/` and the ledger are fingerprinted around the proof, and any change is `HUMAN` with nothing logged. Test steps still run PR code: run the gate in a job with no secrets and `persist-credentials: false` |
| Push after the proof | The merge is pinned to the proven commit (`--match-head-commit`) |
| PR test code rewrites the verdict file after the gate writes it, so every field in it is attacker-controlled | The file is trusted for one fact only — that the proof held. `apply` re-derives kind and the tamper rules from the fetched diff (the same `inspect()` the gate uses), re-decides with the apply job's own ledger and a fresh CI read, takes the PR from its own `--pr` flag (a file naming another PR is refused, so a proof never transfers between PRs), requires its `--agent`/`--model`/`--skill`/`--attempt`/`--issue` flags to match the file, re-checks PR state, head SHA and agent identity, and pins the merge to the gated head SHA. A closed/moved/non-agent PR is refused with nothing written; a file that disagrees with any re-check is refused with `HUMAN`, commented and labeled `needs-human`, with nothing merged or logged; a MERGE can only be lowered (red CI → RETRY), never raised. Note text from the file is validated (≤ 3 notes, ≤ 300 chars, no newlines/backticks/control characters) and never posted |
| PR code reads credentials | Test runs get an environment with `*TOKEN*`, `*SECRET*`, `*PASSWORD*` and `*API_KEY*` variables removed |
| Shell injection through file names | Changed paths outside `[A-Za-z0-9_@+./-]` (or starting with `-`) are tampering, and the runner refuses them |
| The PR edits the gate workflow so a weaker copy gates its own CI | The PR workflow triggers on `workflow_run`, which always runs the default-branch definition — the PR's edited copy never executes; editing `.github/**` is a tamper rule anyway (`HUMAN`, no retry) |
| A push lands after the CI run that triggered the gate, so the gate judges (and apply merges) a commit the repo's CI never covered | The workflow passes `--head <sha>` (the head whose CI completed) to both jobs; `check` stands down with `HUMAN` and no proof runs when the live head differs, and its verdict file names the CI'd commit so `apply`'s moved-head check refuses it with nothing written. The push's own CI fires a fresh gate run |
| The agent forges its own dispatch context (issue number, skill, attempt) on the PR | The PR workflow reads only comments authored by `github-actions[bot]` — the dispatch marker for issue/skill, `Mergeproof — RETRY` comments for the attempt count — and ignores every other author; agent and model come from repo variables, never the PR |

### What remains in the issue flow (prompt injection)

The trusted issue file closes the untrusted channel, not the trusted one:

- A trusted author — anyone in `MERGEPROOF_AUTHORS`, any write/maintain/admin collaborator, or a writer who vouches by re-applying the `agent` label — can still instruct the agent. That is what trust means here; the gate bounds what the resulting PR may do (proof, tamper rules, capped retries), not what the prompt says.
- The agent still reads the repository's own files — code, README, docs, comments in source. Text planted in the repo itself reaches the agent the same way and is not filtered; the gate's proof and tamper rules are the bound.
- The label vouch covers the title and body as they were when the writer added the `agent` label, and counts only when the last `agent` label came from a trusted user (triage can add labels without write access). A body edit (GitHub's `lastEditedAt`) or a title rename after that label, or the label's removal, makes it stale, and the run stops until a writer re-applies the label. Comments do not stale it — they are filtered by author instead. The check reads the issue's history through GraphQL; if that read fails, the run stops too. An author can therefore force a retry of a label-vouched issue back through a writer by editing it; that is a nuisance (fail closed), not an injection.
- On the claude path the agent holds `MERGEPROOF_BOT_TOKEN` and can push and open PRs; on the agy path only the publish job does, and it never runs agent code. Either way, scope it as a fine-grained PAT for this one repository with `contents: write` and `pull-requests: write` only — no workflows, no admin, no org scope — so even a fully injected agent cannot do more than propose a PR the gate still has to prove.

## Workflow permissions

Every job of every template (`templates/workflows/`), what it may do, which secrets it sees, and whether it runs PR code. `mergeproof-pr.yml` grants nothing at the top level (`permissions: {}`) and each of its jobs declares only what it needs; `mergeproof-issue.yml` declares scopes at the workflow level for its `agent` job, while the agy path's `agy-run` and `agy-publish` jobs declare their own (read-only for the run, the publish scopes for the landing); `mergeproof-sync.yml` declares its scopes at the workflow level. Every job checks the `MERGEPROOF_MODE != 'off'` kill switch first. The apply job's checkout deliberately KEEPS its credentials: it never runs PR code, and its ledger push needs `github.token` — only the gate job (which does run PR code) and the issue workflow's agent-side checkouts (`agent`, `agy-run`, `agy-publish`) use `persist-credentials: false`.

| Workflow | Job | Permissions | Secrets it sees | Runs PR code |
|---|---|---|---|---|
| `mergeproof-pr.yml` | `context` | `pull-requests: read`, `issues: read` | none | no |
| `mergeproof-pr.yml` | `gate` | `contents: read`, `pull-requests: read`, `checks: read`, `issues: read`; `persist-credentials: false` | none | **yes** — the proof worktrees execute the PR's tests; read-only `github.token`, no write permission, no secrets |
| `mergeproof-pr.yml` | `apply` | `contents: write`, `pull-requests: write`, `issues: write`, `checks: read`, `actions: write` | none (`github.token` only — its comments are `github-actions[bot]`-authored so the attempt count works, and the agent's bot token never merges; merged commits do not trigger push workflows, the gate pinned the merged head's CI instead) | no — never installs, never checks out the PR |
| `mergeproof-issue.yml` | `agent` | `contents: read`, `issues: write`, `pull-requests: write`, `actions: read`; `persist-credentials: false` | `MERGEPROOF_MODEL_KEY`, `MERGEPROOF_BOT_TOKEN` (both only inside the claude agent step; on the agy path this job runs no agent at all, it only builds the trusted issue file and uploads it as a one-day artifact) | no — runs the agent on the default branch; PR code belongs to the agent, not an untrusted author |
| `mergeproof-issue.yml` | `agy-run` | `contents: read`; `persist-credentials: false` | `MERGEPROOF_MODEL_KEY` (as `GEMINI_API_KEY` inside the agy step, the only secret in the job; no token, no credential helper, no `gh` call) | **yes**: agy itself, untrusted code with no GitHub credential, inside a digest-pinned container on a copy of the checkout (no runner state, no Docker socket); it cannot push, comment or read the API, and its output leaves as a bundle the publish job validates |
| `mergeproof-issue.yml` | `agy-publish` | `contents: read`, `issues: write`, `pull-requests: write`; `persist-credentials: false` | `MERGEPROOF_BOT_TOKEN` (only in the push/PR and stop-comment steps; the marker and refusal comments use `github.token`) | no — never runs agy, npm or repo code; treats the artifact as untrusted data |
| `mergeproof-sync.yml` | `sync` | `contents: write`, `issues: write`, `pull-requests: read` | none (`github.token` only) | no |


## `mergeproof init`

`init` writes only what its report lists: `.mergeproof.json` (always `mode: shadow`), the three workflow templates from `templates/workflows/` with their two placeholders filled, byte-for-byte copies of the bugfix and feature skills under `.mergeproof/skills/`, the `agent` and `needs-human` labels, the `MERGEPROOF_AGENT` / `MERGEPROOF_MODEL` / `MERGEPROOF_BOT_LOGIN` (and, when set, `MERGEPROOF_MODEL_BASE_URL`) repository variables, and the `MERGEPROOF_MODEL_KEY` / `MERGEPROOF_BOT_TOKEN` secrets. It never creates the ledger branch, never changes branch protection or any other repository setting (those are printed as guidance for the maintainer), and never overwrites an existing local file without `--force`. Secret values are read from the environment variables of the same name and travel to `gh secret set` on the child process's stdin only — never in argv, files or log output — and any error message gh produces is truncated to its first line and redacted of the value before it is shown.

## This repository

`main` here is a free private repo, so it has no branch protection: any token with `repo` scope can push to it. `.github/workflows/main-guard.yml` makes that visible: a force-push, a commit that is not part of a merged PR, or a PR merged before its GitHub Actions checks were green fails the run and opens an issue. It detects, it does not prevent: the push runs its own copy of the guard, so a deliberate writer can weaken it in the same push. A public repo or GitHub Pro is needed for enforcement.

## What mergeproof does not do

- No telemetry. Nothing is sent anywhere except the GitHub API calls made through your own `gh` login.
- No model calls. The gate is deterministic code.
- No token handling. GitHub access goes through `gh`; in Actions, tokens stay in the repository's secrets.
